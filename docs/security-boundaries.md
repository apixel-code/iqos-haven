# Security boundaries and implementation controls

Architecture sections 3, 9 and 11 are authoritative. Implemented controls include validation/logging/lifecycle, backend sessions/permissions/reset/invitations/staff administration, Origin/CSRF/rate limits, the gateway, private storage and service auth (steps 18–38). Admin auth UI now uses the real same-origin API; age tickets and commerce enforcement remain pending milestones.

| Boundary                         | Required enforcement                                                                                                               | Release evidence                                                                                      |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Browser → same-origin gateway    | Origin/content-type checks; host-only cookies; strip client trust/age headers                                                      | Actual admin/store origins and CSRF tests                                                             |
| Gateway → private API            | Network allowlist + service identity; no public internal routes                                                                    | Origin-bypass/forged-header denial                                                                    |
| Browser → gateway (step 29)      | Allowlisted /api prefixes per origin; trust headers stripped; gateway-owned request ID/client IP; 64 KB API bodies; SSE unbuffered | `pnpm test:gateway` (29 checks, real Caddy); Cloudflare trusted ranges + origin restriction per BI-06 |
| Service → internal route         | HMAC service auth (`@InternalService`): key id, ±30 s window, nonce, body hash; never cookies                                      | Implemented step 26 (guard tests); private network still required                                     |
| Service → object storage         | Private buckets, least-privilege service identity, presigned URLs ≤ 15 min, POST policy size/key/type                              | Implemented step 26 (MinIO tests); provider IAM per BI-06                                             |
| Store → restricted content       | Ticket signature/audience/policy; HTML/RSC/API/metadata/media cache safety                                                         | AGE-01–06                                                                                             |
| API → database                   | Runtime role separate from owner; parameterized SQL; explicit locks/constraints                                                    | Commerce races and FK/deletion tests                                                                  |
| Worker → DB/Redis/providers      | Durable effects and idempotency; bounded leases/retries; no network in DB tx                                                       | Crash/loss/provider acceptance drills                                                                 |
| Upload → quarantine → derivative | Permission/byte/type/dimension checks; no executable original exposure                                                             | Upload attack samples                                                                                 |
| Staff → Owner fields/reports     | Action/field/requester scope rechecked server-side                                                                                 | Direct endpoint/ID/field denial                                                                       |
| Logs/telemetry/export            | Allowlisted IDs/codes/static messages; no body/query/URL/PII/SQL/raw errors                                                        | Recursive logger tests plus real telemetry review                                                     |
| Release/restore → customer sends | Separate credentials/state; sends disabled in drills/staging                                                                       | Recipient routing and isolated restore evidence                                                       |

Structured logging removes sensitive keys/URL/body/headers and exception text recursively with bounded depth. It cannot discover a secret placed inside an arbitrary static-message argument or an innocently named string field; log call sites must use only approved fields/static messages. Extend checks when payload shapes change. No API serializer logs raw URLs.

API request body limit is 32KiB for the current JSON foundation. New bounded schemas must be strict at nested object boundaries too. Gateway/upload/media limits are separate and must be implemented with those features. Missing body/query DTO contracts fail rather than permitting unchecked input. Future route parameters and controlled business error codes must use shared contracts.

Production credentials and key purposes remain separate. Secrets are never copied into this ZIP, docker build context, browser bundle or build cache. Provider/profile, CSP/TLS/WAF, retention, IAM and production grants still require actual selected infrastructure and tests.

Staff administration writes recheck active `staff.manage` authority after Owner-role and sorted user locks. Required aggregate versions reject stale edits; last-active-Owner checks serialize deactivation. Email edits/deactivation revoke sessions, reset verifiers and pending issued invitations atomically with audit/outbox. Session creation verifies identity version as well as password hash under the user lock, fencing pending old-email logins. Fixed-role changes/reactivation use the same shared identity transaction support (step 36), preserve saved credentials and revoke old capabilities. Concurrent demotion/deactivation cannot remove the last active Owner; frontend identity UI is implemented in step 37.

Admin auth/session pages are dynamic and no-store. Browser requests send same-origin cookies and bounded JSON through `/api`; no session token enters JavaScript. Reset/invite fragment capabilities are kept only in a component ref and removed from history before requests. Session verification rechecks on route/focus/visibility and every minute, aborts superseded reads, hides protected content on failed verification and redirects 401 to sign-in. Navigation/direct-section guards derive only from current server permissions; API authorization remains required for each operation. No prototype credentials or browser identity storage are used. Visual/interactive browser verification still needs an enabled Computer Use surface.

Typed settings are Owner-only via current `settings.manage`, with no public read or seed defaults. Required versions serialize first creation and later edits. Writes stabilize actor authority under the common Owner guard before locking configuration keys, then commit metadata-only audit and IDs-only outbox atomically. Contact/recipient/template values are omitted from audit/events. Clearing uses JSON-null without deleting aggregate history. Configuration values contain no provider credentials; storing notification toggles cannot activate customer sends in this step.
