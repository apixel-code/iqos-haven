# 0007 — Staff invitation lifecycle and approved role snapshots

- Date: 2026-10-10
- Status: accepted
- Step: 34

Architecture §11 requires single-use expiring/revocable invitations and a role approved by the server, never by the invitee. The recipient has no account until acceptance. Only a current active `staff.manage` holder can issue/revoke; launch grants make this Owner-only. New accounts may be Owner or Staff, as approved by that operator. Existing accounts, including inactive ones, are never overwritten or reactivated by this flow. Managing existing staff remains steps 35–36.

Invitations expire after 24 hours (a fixed initial policy; staging/operator review may revise it). PostgreSQL stores the normalized email/name and approved role/actor as immutable snapshots, a hashed verifier and key ID, expiry, accepted/revoked timestamps and a version. The terminal states cannot be undone; accepted and revoked are mutually exclusive. One pending row per normalized email is enforced by a partial unique index. Resend atomically revokes the prior snapshot and issues a new one, with audit/outbox for both. No pending user or default password is created. Issue responds with invitation ID/expiry so the authorized operator can revoke it; no secret returned. Existing-account issue returns generic 409 to that authorized operator only. Public acceptance errors are generic 400.

Issue/reissue/revoke/accept take the common Owner-role lock, then the inviting staff row, then the invitation row/new user insert. This includes Staff invitations for a simple common lock protocol; it serializes invitation mutations globally and is acceptable under the initial 30/hour management budget. Owner insertion is protected by the existing DB membership trigger as well. Authority is rechecked inside the transaction (including acceptance), preventing demotion/deactivation from racing a privileged write. Currently unauthorized inviters' pending links are refused until authority is restored or the invitation explicitly revoked. Acceptance rechecks expiry/use/revocation/recipient uniqueness under locks, creates exactly one account with the saved role, and writes audit/outbox atomically. Password normalization/validation/argon2 hashing happens outside transactions; acceptance repeats the security checks afterwards. No auto-login. Concurrent account creation may win uniqueness; the invitation never replaces it.

Durable delivery follows ADR 0006 with a separate key ring and PRF purpose: `STAFF_INVITATION_KEYS=invite:keyId:base64urlSecret` (>=32 random bytes, independent from reset/internal keys) and `STAFF_INVITATION_ORIGIN` (bare admin origin; HTTPS in deployed environments). Random UUID selector + purpose-keyed 256-bit secret; only SHA-256 stored, IDs-only event payload. Worker reproduces the same token under its stored key ID, verifies it, and suppresses expired/accepted/revoked invitations, existing recipients' accounts or currently unauthorized inviters. The immutable snapshot keeps retry content/recipient stable. Email links use `/invite/accept#token=...`; step 37 will consume/clear the fragment without persistent browser storage.

Empty keys disable issue/accept with 503; revoke remains available. Rotate readers first and retain old keys through the last 24-hour expiry and rollout. Removing a delivery key does not revoke an already delivered verifier: compromise response must revoke unused rows by key ID and audit the incident. Database dumps alone cannot reconstruct links; combined access to the key and selectors can. Email already in flight may arrive after revocation, but its link cannot be consumed. SMTP duplicate risk and disabled/allowlist behavior are unchanged. New event types need no historical backfill.

Management and acceptance have separate fail-closed policies (management IP/actor 30/hour; acceptance IP 20/15 minutes). Denials are generic 429 with Retry-After; authoritative limiter outages return 503. Origin/JSON rules apply. UI is step 37, real identities BI-11, real email go-live BI-07. No milestone gate closes here.
