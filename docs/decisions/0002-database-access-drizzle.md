# 0002 — Database access: Drizzle ORM + node-postgres

- Date: 2026-10-07
- Status: superseded by ADR 0003; retained as historical context
- Step(s): 14

## Context

Commerce correctness needs explicit transactions (READ COMMITTED), row locks in canonical order, `FOR UPDATE SKIP LOCKED` for the outbox relay, real constraints, and SQL-first migrations reviewable in PRs.

## Decision

- **Drizzle ORM** (`drizzle-orm/node-postgres`) with `pg` Pool. Schema in `packages/db/src/schema`, SQL migrations generated by **drizzle-kit** into `packages/db/migrations` and committed.
- One transaction helper: `withTransaction(db, tx => …)` (READ COMMITTED). Repositories take `DbExecutor` (db or tx), never open their own transactions.
- `sortedForLocking()` for deterministic lock order inside a group.
- Migrations run with the owner role (`DATABASE_MIGRATION_URL`); apps use the least-privilege runtime role (`DATABASE_URL`, `ih_app`).
- Raw `sql` is allowed for locking clauses and reporting queries; identifiers are never interpolated from user input.

## Alternatives considered

- Prisma — weaker control of locking/`SKIP LOCKED` inside interactive transactions; heavier runtime.
- Kysely — good fit, but no first-party migration generation; would need hand-written migrations.
- TypeORM — implicit behaviour (cascades, lazy relations) conflicts with "history never cascades".

## Consequences

- Generated migration SQL must be reviewed for expand/contract compatibility before merge.
- Never read the generated `migrations/meta` snapshots into Claude's context.
