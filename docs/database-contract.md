# Database contract and migration plan

Prisma 7.10.0 + pg adapter, PostgreSQL 18. The source schema is `packages/db/prisma/schema.prisma`; generated client code is disposable build output. **No business tables are implemented yet.** The empty client supports the health/raw-query/transaction foundation without adding invented tables.

## Rollout and constraints

Follow the existing roadmap's Database migration rollout table. Generate/review SQL per module with `pnpm db:migration:create --name <module>`, commit migration.sql and migration_lock.toml, then regenerate the client. Do not run dev migration/reset against staging/production. Runtime role may not perform DDL. `pnpm db:migrate` fails on missing/empty bundles; only local empty scaffold may use `--allow-empty` with APP_ENV=development.

Use UTC timestamptz, UUIDv7, bounded integer fils/basis points and safe wire serialization. SQL constraints enforce nonnegative stock/money, positive quantities, SKU/slug/signature/key uniqueness and explicit FK ON DELETE behavior; append-only ledgers cannot be overwritten/deleted by ordinary runtime commands. Review runtime grants/append-only triggers when each table arrives. The local blanket CRUD default is infrastructure convenience, not the final per-table permission policy.

## Transaction/lock policy

Read Committed. Resource order: idempotency claim → existing order if used → mutated customer → sorted settings/delivery-area → catalogue parent/price → coupon → variants. Relevant price/config/published rows use FOR SHARE; mutable counters/balances use FOR UPDATE/conditional writes. Never acquire an earlier group after a later one; imports and all admin writes use the same inventory rules. Existing transaction helper restarts the whole transaction for Prisma P2034 at most three attempts, with jitter and bounded waits; unique-key failures roll back before a fresh winner lookup. Commit-time/error-code behavior must also pass real PG tests.

No network I/O inside transactions. Durable event/effect requirements and successful idempotency response commit with the order. Root DbExecutor is valid for non-transactional reads; commerce writes inside a unit of work must receive only its Tx. A common transaction context is not permission to mix root writes with Tx writes.

## Query/retention review

Use architecture's query-specific indexes: status/date/id, customer/date/id, collected_at, variant activity, stock ledger and incomplete-effect partial indexes. Measure EXPLAIN ANALYZE with realistic data; do not index every combination. Preserve historical snapshots/deletion references, versioned report definitions and privacy retention from BI-08. Review each migration's expand/deploy/contract compatibility and rollback window.
